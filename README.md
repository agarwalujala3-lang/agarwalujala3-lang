## Engineering focus

I build end-to-end product surfaces where the engineering is easy to evaluate: frontend workflows, server-side APIs, deployment configuration, source-backed explanations, and release checks sit together in the open.

- **Full-stack product delivery** — responsive interfaces paired with Node.js and Express service layers.
- **AI-assisted workflows** — practical systems for knowledge transformation and repository understanding, with evidence and fallback paths made explicit.
- **Cloud-aware architecture** — serverless AWS design across auth, APIs, storage, OCR, and data flows; public demos keep credentials and private data out of the browser.
- **Quality as a feature** — clear demo/production boundaries, source-linked reasoning, automated checks, and deployment-ready documentation.

## What a reviewer can verify

| Signal | Where to inspect it |
| --- | --- |
| Product execution | Live deployments, user flows, responsive UI states, and project documentation |
| Backend ownership | Express routes, API contracts, service boundaries, server-side configuration, and deployment files |
| Practical AI use | Source-grounded repository exploration, optional AI assistance, and AI-powered knowledge workflows |
| Cloud judgment | AWS architecture paths, safe public demo modes, no static secret exposure, and configuration-led live integration |
| Engineering discipline | README boundaries, smoke and regression scripts, GitHub Actions, audit commands, and visible trade-offs |

## Working principles

- Build the path a real user would follow, not just an attractive landing page.
- Make claims traceable: link to the live product, source, documentation, or the exact evidence behind an explanation.
- Treat a public demo as a trust surface—label what is simulated, protect credentials, and keep private data out of the experience.
- Prefer useful constraints over vague promises: what a system can verify, infer, or not know should be visible.
